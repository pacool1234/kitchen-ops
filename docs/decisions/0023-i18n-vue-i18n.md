# 0023. Internationalisation: vue-i18n, Spanish first, amounts formatted from decimal strings

- Status: Accepted
- Date: 2026-10-18

## Context

The restaurant works in Spanish, with English as a second language (spec section 11.1, an assumption under decision 0020). Every string must go through i18n from the first screen, and amounts must be shown the Spanish way: `1.234,56 €`, `18/10/2026`, `2,5 kg`. Money is never a JavaScript `number` (CLAUDE.md, decision 0015), and the web app may depend only on `shared`, so it can't use the ledger's fixed-point code to format it.

Spec section 11.3 proposed vue-i18n.

## Decision

**vue-i18n,** in its Composition API mode, with Spanish (es-ES) the default and English (en-GB) second.
- **The messages are TypeScript files** (`apps/web/src/i18n/messages/`). `es.ts` is the source, and `en.ts` is typed from it, so a missing or extra key fails the typecheck. Tests check the same keys and placeholders in both, and that every message compiles.
- **`useT()` takes only keys that exist.** vue-i18n's own `t` accepts any string, and its key types only drive autocompletion.
- **Lint refuses raw text in templates** (`vue/no-bare-strings-in-template`).
- **API errors stay codes,** which the web app translates (`errors.forbidden`).

**Each user's language is saved by the API:** a `users.locale` column, changed by `PATCH /api/me`, and returned by `GET /api/me`.
- Before sign-in, the app shows the language this device last showed, or Spanish.
- After sign-in, it shows the user's saved language, so a shared tablet doesn't keep the previous user's. A language chosen on the sign-in page just before is saved as theirs.
- `<html lang>` always follows the language shown (WCAG 3.1.1).

**Amounts are formatted with `Intl.NumberFormat`, from strings.** Since its version 3 (Baseline 2023), `Intl.NumberFormat` formats a decimal string exactly, digit by digit, however large. So money goes from `bigint` cents, or the API's decimal string, to a string, then to Intl, and never through a `number`. Property tests read the output back for amounts well beyond 2^53.
- **Grouping is always on** (`1.234,56 €`), though es-ES leaves 4-digit amounts ungrouped by default, so a column of amounts reads the same throughout.
- **Unit costs are shown per kilo, litre or unit** (`18,50 €/kg`): a base unit is a gram, a millilitre or a thousandth of a unit, so this moves the decimal point 3 places and loses nothing.
- **Times are shown in the restaurant's time zone,** Europe/Madrid, whatever the device's.

## Alternatives considered

- **Messages as JSON files.** They're the common format for translators, but typing keys from JSON needs a build plugin. TypeScript files give the same checks with no tooling. Moving to JSON later, if a translation service needs it, is mechanical.
- **Formatting money with a decimal library** (decimal.js, big.js). It would work, but it's a dependency for what Intl already does exactly from a string.
- **The language saved on the device only** (`localStorage`). It's simpler, but the issue asks for a per-user choice, and staff share devices.
- **Better Auth's `update-user` to save it.** It would bypass the contract (decision 0022); the field is `input: false` there, like the role.
